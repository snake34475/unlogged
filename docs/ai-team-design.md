# 《未登录的人》AI 协作角色设计

本仓库现提供两个项目级 Skill：`.codex/skills/unlogged-experience-review/SKILL.md` 与 `.codex/skills/unlogged-development/SKILL.md`。可在 Codex 中明确指定 `$unlogged-experience-review` 或 `$unlogged-development`；自然语言任务也会按 `AGENTS.md` 的条件选择相应工作流。Skill 不会单独创建一个并行模型；如需独立评审与开发 Agent 同时工作，请在请求中明确要求多 Agent 协作。

使用示例：`请用 $unlogged-experience-review 检查第一章的拒绝路线`；`请用 $unlogged-development 实施方案 A`。名称中的连字符属于 Skill 名称；单写 `@unlogged-experience-review` 或把它改成下划线名称，不会调用这两个 Skill。自动匹配依赖任务表述与 Skill 描述，明确指定 `$名称` 更可靠。

## 当前已构造的两个角色

本次评审采用两个职责分离的 AI 角色：

1. **体验评审 AI（Experience Reviewer）**
   - 使命：以首次玩家视角审查 UI、叙事连续性、选择语义、节奏、可重玩性和同类作品的结构差距。
   - 输入：可玩的 Web 版、故事圣经、章节流程、角色母版。
   - 输出：按严重性排序的问题、证据、体验假设、验收标准；不直接改代码。
   - 禁区：不以“像某作品”为目标，不引入参考作品的具体内容。

2. **开发 AI（Development Agent）**
   - 使命：把已确认的体验目标拆为 Web/Ren'Py 数据、运行时、UI、资产和验证任务，并控制双版本漂移。
   - 输入：已确认的方案、AGENTS.md、故事规则和现有实现。
   - 输出：文件级实施计划、最小变更集、技术风险、构建与三结局验证结果。
   - 禁区：没有经体验评审确认的叙事方向时，不自行扩写章节或替换角色规则。

这两个角色足以推进方案 A 或 B：评审 AI 先定义“为什么改、改到什么程度”，开发 AI 再定义“如何实现、如何验证”。角色分离能避免开发过程中把可构建误当作体验已经成立。

## 推荐工作流

```text
体验评审 AI：提出问题与验收标准
        ↓
主负责人：选择方案、冻结本轮叙事目标
        ↓
开发 AI：拆分并实现最小变更
        ↓
体验评审 AI：按验收标准复测
        ↓
主负责人：决定扩写、返工或进入下一章
```

每轮只选择一个可验证目标，例如“拒绝好友后，玩家能感到自己仍在拒绝，并看到异常如何越权”。不要用“提升氛围”这种无法验收的任务描述。

## 是否还需要更多 Agent

**现在不建议超过两个常驻 Agent。** 第一章内容规模仍小，过早拆成大量角色会增加沟通成本和相互矛盾的文案。以下角色在对应条件出现时再临时加入：

| 触发条件 | 临时角色 | 负责内容 |
|---|---|---|
| 开始方案 B 的互动与分支改写 | 叙事系统设计 AI | 将故事写成节点、状态、证据和结局条件；维护流程图 |
| 需要新头像、界面故障图、宣传图 | 视觉/资产 AI | 先读角色母版；保持 N 不提前展示真人脸与现有冷色视觉语言 |
| 增加音效、环境声或音乐 | 音频演出 AI | 定义声音触发表、响度层级、静音/移动端降级策略 |
| 准备公开发布 | 发布 QA AI | 全分支、移动端、字体子集、Web 构建、双版本一致性检查 |

方案 B 推荐以 **3 个并行职责上限** 工作：主负责人 + 体验评审 + 开发 AI。需要资产或发布时，再用临时角色替换空闲角色；不建议让四个以上角色同时编辑同一仓库。

## Skill 配置建议

- **评审与开发：使用仓库内上述两个 Skill。** 它们保存项目特有的判断边界与交付标准；普通请求可自动匹配，也可用 `$名称` 指定。
- **制作新位图资产时：使用 `imagegen` skill。** 必须先读取 N 与主角的角色母版，并保持第一章不展示 N 的真人脸。
- **需要关系图、分支图或玩家路径可视化时：使用 `visualize` skill。** 它适合验证状态如何流入各结局，但不应代替游戏内 UI 实现。
- **需要发布用说明、试玩反馈表或设计文档时：按目标格式使用文档/PDF skill。** 普通 Markdown 文档不需要这些 skill。

目前没有必要为“Galgame 制作”安装泛用 skill。若未来反复执行字体重建、双端同步与三结局验证，再考虑新增专门的发布 QA Skill。

## 交接模板

每次向开发 AI 下达任务，应包含以下五项：

1. 玩家体验目标（例如：拒绝不是无效选项）。
2. 不可触碰的叙事边界（例如：N 的真实身份不在第一章解释）。
3. 指定路径与运行时（Web、Ren'Py，或两者）。
4. 可观察的验收条件（例如：拒绝线显示临时会话且保留一条后续专属反应）。
5. 验证范围（构建、三结局、390px 移动端、字体更新）。

每次向体验评审 AI 交接时，应提供实际试玩入口或改动摘要，并要求其从“玩家能否感知”而非“代码是否存在”角度判定结果。
