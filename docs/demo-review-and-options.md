# 《未登录的人》第一章：体验评审与改造方案

评审日期：2026-09-30
评审范围：Vite + React Web 版第一章、Ren'Py 原型、桌面与 390 × 844 移动端试玩。

## 结论

当前版本已经具备一个有效的开场钩子：深夜的陌生好友申请、N 对日常细节的异常知情，以及冷色的房间与聊天界面。它成功让人想问“她为什么会知道”，但尚未让玩家真正感到“我的回应改变了什么”。因此它目前更接近高质量气氛短片，而不是以选择和人物关系驱动的 Galgame Demo。

最应该优先修复的不是扩写第二章，而是让第一章的选择产生即时、持续且可被玩家察觉的后果，并让异常按可验证的证据链逐步升级。

## 已验证的现状

- Web 生产构建通过：`npm run build`。
- 桌面首屏的阅读层级清晰；390 × 844 移动端可完整使用，但选项与“点击继续”提示偏小、对比偏弱。
- Web 叙事流程共有三个选择点，选择后基本立刻回归主线，最终由三项隐藏倾向分配结局。
- 菜单中“成就”“图鉴”“存档管理”目前为占位内容；“章节选择”只会关闭菜单继续当前进度。
- 当前 Web 版没有实际声音演出；资产清单已将环境音、消息提示、手机震动和异常低频音列为待补项。

## 问题清单（按优先级）

### P0：选择不够可信，后果过晚且不可见

“同意 / 拒绝 / 查看资料”以及后续两次态度选择都只加隐藏数值，随后迅速汇流。玩家无法从台词、界面或可操作内容中感知自己的态度留下了什么。尤其在“拒绝”后，页面仍直接打开 N 的正式聊天窗口并标记“在线”；它可被解释为异常，但当前没有界面层面的说明，因此更像选择没生效。

**建议**：为信任、好奇、回避各设计一个持续状态和一个中段专属事件。状态应改变 N 的称呼、信息呈现方式或玩家能查看的记录，而不是只在结局处结算。

### P0：隐藏倾向与选项语义冲突

“你在我电脑里装监控？”和“你到底想做什么？”均增加信任；从玩家语义看，前者明显是戒备，后者是追问。隐性数值本身没有问题，但不能违背玩家对自己行为含义的直觉。

**建议**：保留隐藏数值，但以可感知的态度来设计选项。信任应是“我愿意听你解释”，好奇应是“给我证据/我去验证”，回避应是“别再联系我/我退出”。

### P0：异常升级跳跃，缺少因果和验证

N 从知道“刚刚打开游戏”很快跳至“我就在你旁边”，而玩家没有一次主动验证、反驳或失败的过程。恐怖信息出现了，但悬疑没有积累。

**建议**：采用五步节奏：可解释的巧合 → 记录矛盾 → 玩家验证 → 验证被改写或失败 → 近距离威胁。每一步都应改变可见界面或可操作对象。

### P1：聊天 UI 与叙事 UI 重复表达同一句话

当前发言在底部对话框展示的同时，也已写入聊天气泡；聊天窗口主要承担“最近四句”的重复展示。结果是 UI 很漂亮，却还没有成为叙事玩法。

**建议**：聊天气泡承担人物消息；底部框只承载旁白、系统异常和关键选择。对话历史可做成真实聊天记录，并让“撤回”“输入中”“灰色头像”“时间戳”成为线索。

### P1：第一处选择塑造了“点什么都一样”的预期

“打一局”“早点睡”“看 QQ”都会在极短文本后导向好友申请；其中“早点睡”还会强制重新打开电脑。作为人物行为可以成立，但对玩家而言是一个很早出现的假选择。

**建议**：让三个开场分别留下不同证据：游戏启动记录、合盖后的在线状态、好友列表中的旧头像。N 应根据该证据说出不同的第一句异常台词。

### P1：三个结局是三句收尾，尚未成为三种结果

三个结局只在末尾数句分叉，缺少专属事件和情绪高潮。“明天见”的“找一个人”把玩家刚做出的赴约意愿转向未建立的目标；“她从未存在”立刻以短信否定“消失”，也弱化了前一秒的空白。

**建议**：让每个结局回答不同问题：信任线回答“回应的代价”，好奇线回答“记录为何无法保存”，回避线回答“拒绝是否真的能退出”。

### P2：演出与系统承诺不匹配

单一背景、头像和文字可以支撑原型，但不足以持续承接都市异闻的紧张感；无提示音、无输入提示动画、无退出/断线的声画变化，会使异常主要停留在台词层面。菜单中开放却为空的成就、图鉴也容易制造落差。

**建议**：先补最小音频包和四类微演出，后补内容系统；在系统实际可用前隐藏菜单入口或标注“开发中”。

## 作品参照：借鉴结构，不复制内容

《千恋＊万花》值得借鉴的是“选择沉淀为角色关系与路线体验”：玩家先在日常互动中在乎角色，再把选项理解为关系选择。当前 N 的概念明确、语气有潜力，但与玩家还没有足以支撑“愿不愿意回应她”的情感积累。

《命运石之门》值得借鉴的是“规则以事件和后果被玩家理解”：异常不是一句更大的设定，而是不断限制或改变角色能做什么。当前的“23:47”“记录异常”“N 知情”都是很好的种子，但应让玩家亲手查看、验证，并承担验证失败的结果。

不应复制上述作品的角色、设定、事件、台词或视觉符号；本项目应继续保持“普通通信工具侵入现实”的独立核心。

## 三种可执行方案

### 方案 A：可信回应（低风险修整）

**目标**：在不扩大章节规模的前提下，让现有 8–12 分钟流程变得连贯、选择可信、可再次游玩。

**范围**：

- 重写三处选项，使其文字与隐藏倾向一致；每条路线至少保留一句后续专属回应。
- 将“拒绝后正式聊天”改为“陌生人临时会话”，或以显著系统异常解释其越权出现。
- 三种开场分别对应 N 的第一条知情证据。
- 让三结局各增加一个专属可见界面变化，并在结尾给出“已发现的异常”回顾。
- 增加消息提示、输入中、断线、手机震动四个短音效/动效；隐藏未实现菜单页。
- 统一 Web 与 Ren'Py 文案和结局线索。

**适合场景**：要尽快获得可投递、可展示的 Demo；现有美术和章节长度基本保留。

**验收标准**：玩家能在不看攻略的情况下说明三个选择分别代表何种态度；任一路线至少有两处玩家可察觉的专属反馈；三个结局不再只替换最后几句文本。

### 方案 B：可验证的异常（推荐）

**目标**：将第一章升级为 15–20 分钟的可玩悬疑垂直切片，使聊天程序成为玩法而非背景。

**范围**：

- 方案 A 全部内容。
- 新增三次轻交互：查看资料/账号注册记录、查看聊天时间戳或撤回消息、尝试退出或查看手机短信。
- 采用“巧合—矛盾—验证—改写—威胁”的五段结构；每条态度路线有一个不同的验证结果。
- 聊天消息从底部框迁入聊天窗口；底部框仅保留旁白、系统和选择。
- 建立 3 个实际可解锁的结局记录或异常档案；结局后可回看已获得线索。
- 增加聊天窗口状态：陌生人会话、好友、离线、输入中、消息撤回、时间冻结。

**适合场景**：希望用一章证明核心卖点，并为第二章建立可复用的叙事运行时。

**风险**：Web/Ren'Py 双实现会扩大同步成本；需要先确定 Web 为唯一发布版本，或将共享剧情数据/行为规范抽出。

**验收标准**：试玩者能复述至少两条由自己操作发现的异常；不同路线的中段体验明显不同；结局档案能解释“我为什么值得重玩”。

### 方案 C：第一章垂直切片（完整 Demo）

**目标**：制作 25–35 分钟、具备公开展示质量的第一章，明确人物吸引力、核心玩法和后续章节承诺。

**范围**：

- 方案 B 全部内容。
- 增加一段 N 与玩家的日常交流，以及一段来自“白色外套女孩”的现实线索；两者都服务于 N 的“确认玩家会不会回应”动机。
- 每条态度路线新增一个完整中段场景和一个不同的异常呈现；后段可汇流，但需保留可见状态。
- 补齐环境音、交互音、关键剧情演出；为不展示真人脸的 N 制作头像状态、文字扰动和界面故障，而非提前使用角色立绘。
- 实装结局档案、回放/快进、可访问性设置、真正可用的存档界面，并进行移动端与桌面端完整 QA。

**适合场景**：准备参加展示、征集反馈或作为众筹/发行前的核心样章。

**风险**：内容与资产工作量显著提升；若仍维护两套运行时，叙事漂移会成为主要风险。应先冻结故事规则、确定发布主版本。

**验收标准**：首次玩家能完整理解人物目标、一个世界规则与下章钩子；至少两条路线值得重玩；无未实现菜单入口、无跨版本剧情矛盾、移动端完成全流程。

## 推荐决策

选择 **方案 B「可验证的异常」**。它以有限范围修正当前最关键的体验问题，同时将“聊天记录改写现实”从主题句变成可玩的系统；相较方案 C，也不会在第二章方向尚未确定时过早扩张资产和内容。

## 跨版本维护风险

Web 与 Ren'Py 文案已经漂移：资料页是否显示注册日期、信任结局是“上次在线三年前”还是“从未登录”等关键线索不同。开始任一方案前应明确 Web 是否为唯一事实源；若仍保留 Ren'Py，则为每个节点建立共享流程表，并在每次修改后覆盖三种结局。
